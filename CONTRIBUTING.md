# Правила внесения изменений

Любое изменение считается потенциально ошибочным, кто бы его ни написал и каким бы способом
код ни был создан. В `develop` и `main` попадает только то, что прошло проверки ниже.

## 1. Модель ветвления — GitFlow

| Ветка | Назначение | Откуда создаётся | Куда сливается |
|---|---|---|---|
| `main` | Выпущенные версии. Каждый коммит в `main` помечен тегом `vX.Y.Z` | — | — |
| `develop` | Интеграционная ветка: следующая версия в разработке | `main` | `release/*` |
| `feature/<№задачи>-<кратко>` | Одна функция или задача | `develop` | `develop` (через PR) |
| `release/X.Y.Z` | Подготовка выпуска: версия, документация, исправления | `develop` | `main` и `develop` |
| `hotfix/X.Y.Z` | Срочное исправление выпущенной версии | `main` | `main` и `develop` |

Прямые коммиты в `main` и `develop` запрещены. Изменения попадают туда только через Pull Request.

## 2. Путь изменения

1. **Задача.** Создать Issue на GitHub: что нужно сделать и критерии приёмки.
2. **Ветка.** `git switch develop && git pull && git switch -c feature/12-top-sellers-period`.
3. **Коммиты.** Небольшие и осмысленные, в формате
   [Conventional Commits](https://www.conventionalcommits.org/ru/):
   `feat: ...`, `fix: ...`, `docs: ...`, `test: ...`, `refactor: ...`, `chore: ...`.
   В сообщении или описании PR указывается номер задачи (`#12`).
4. **Локальная проверка.** `make verify` должна завершиться без ошибок.
5. **Pull Request** в `develop` по шаблону: что изменено, как проверено, `Closes #12`.
6. **Проверка.** На PR автоматически запускается GitHub Actions (`make verify`). Автор
   проходит чек-лист ревью из шаблона PR. Красный CI или незакрытые замечания означают,
   что сливать нельзя.
7. **Слияние** — `Create a merge commit` (история коммитов ветки сохраняется). Ветка удаляется.
8. **Выпуск.** `release/X.Y.Z` → обновить версию в `app/__init__.py` и `CHANGELOG.md` →
   PR в `main` → тег `vX.Y.Z` на коммите слияния → слить `main` обратно в `develop`.

## 3. Обязательные команды проверки

| Команда | Что делает |
|---|---|
| `make quality` | `ruff format --check` (форматирование) и `ruff check` (статический анализ: ошибки, импорты, небезопасный код) |
| `make test` | автотесты `pytest` (API, правила предметной области, авторизация, ошибки) |
| `make verify` | `quality` + `test`: **обязательна перед каждым PR**, то же самое выполняется в CI |
| `make migrate` | применение миграций к БД (обязательно при изменении моделей) |

При изменении моделей БД обязательно создаётся миграция:
`.venv\Scripts\alembic revision --autogenerate -m "описание"`. Её нужно проверить вручную.

## 4. Запрещённые действия

- Коммитить секреты: `.env`, пароли, токены, ключи. В репозитории хранится только `.env.example` с заглушками.
- Коммитить локальные файлы: `.venv/`, `logs/`, `*.db`, кэши, настройки IDE (см. `.gitignore`).
- Делать прямой push в `main`/`develop`, `git push --force` в общие ветки, переписывать опубликованную историю.
- Удалять или отключать тесты (`skip`, `xfail`), ослаблять правила `ruff`, добавлять `noqa` без объяснения, ослаблять CI только ради прохождения проверки.
- Сливать PR с красным CI или без прохождения чек-листа.
- Менять уже применённые миграции. Нужна новая миграция.

## 5. Критические файлы приёмки

Изменения этих файлов должны быть явно перечислены в описании PR и проверяться отдельно:
`Makefile`, `pyproject.toml` (настройки ruff/pytest), `tests/`, `.github/`, `alembic/versions/`,
`requirements*.txt`, `CONTRIBUTING.md`.

## 6. Порядок приёмки

Изменение принято, когда выполнено всё:

1. есть задача (Issue) и PR связан с ней;
2. ветка названа по правилам и создана от `develop`;
3. `make verify` проходит локально и в CI;
4. для новой логики добавлены тесты;
5. при изменении схемы БД есть миграция;
6. обновлена документация (`README.md`, `docs/api.md`, `docs/schema.md`), если изменилось поведение;
7. в diff нет секретов и локальных файлов;
8. пройден чек-лист ревью в PR.

## 7. Разрешение конфликтов слияния

1. Обновить базовую ветку: `git switch develop && git pull`.
2. Влить её в свою ветку: `git switch feature/... && git merge develop`.
3. В файлах с маркерами `<<<<<<<`, `=======`, `>>>>>>>` оставить правильный вариант
   (часто это объединение обоих изменений) и удалить маркеры.
4. `make verify`, затем `git add <файлы> && git commit` (коммит слияния) и `git push`.
